# novel-transforms

## Purpose

Answer one question:

> Which open GitHub issues on `Knowledge-Graph-Hub/kg-microbe` are asking us to
> ingest a **new** external data source — one that would produce a new transform
> under `kg_microbe/transform_utils/` — as opposed to fixing / extending a
> transform we already have?

The answer is a moving target: issues open, close, and morph. This skill
regenerates `docs/NOVEL_TRANSFORMS.md` from the current issue tracker plus a
small hand-maintained override list, so the doc stays honest without anybody
having to grep the issues by hand.

## Usage

```bash
# Regenerate docs/NOVEL_TRANSFORMS.md from the live issue tracker (default)
poetry run python .claude/skills/novel-transforms/novel_transforms.py

# Print the table to stdout without writing the file (dry-run)
poetry run python .claude/skills/novel-transforms/novel_transforms.py --print

# Machine-readable JSON (for pipelines / other skills)
poetry run python .claude/skills/novel-transforms/novel_transforms.py --json

# Show which existing-transform matches killed a candidate (useful for tuning)
poetry run python .claude/skills/novel-transforms/novel_transforms.py --verbose
```

Options:

- `--print` — write to stdout, don't touch the file on disk
- `--json` — emit JSON instead of Markdown
- `--verbose` — show the excluded-candidates list with reasons (helps tune
  overrides)
- `--output PATH` — override the default `docs/NOVEL_TRANSFORMS.md` target
- `--limit N` — cap the issue query (default: 1000, effectively "all open")

Exit codes: `0` = wrote successfully / clean dry-run, `1` = `gh` CLI missing or
unauthenticated, `2` = other I/O error.

## How classification works

Each open issue is scored against three signal sets:

1. **Inclusion signals.** Verbs (`ingest`, `add ... transform`, `explore ...
   data`, `integrate ... api`) OR a named external DB / dataset from a curated
   list (see `EXTERNAL_DB_NAMES` in `novel_transforms.py`). If none match, the
   issue is dropped.

2. **Existing-transform names.** If the title/body strongly focuses on a name
   that is already a transform directory under `kg_microbe/transform_utils/`
   (bacdive, mediadive, madin_etal, metatraits, ...), the issue is treated as
   an *enhancement* and dropped from the novel list.

3. **Manual overrides.** Two hand-maintained sets in `novel_transforms.py`:
   - `MANUAL_INCLUDE` — issue numbers to force-include even if the classifier
     rejected them (curator says "trust me, this really is a new source").
   - `MANUAL_EXCLUDE` — issue numbers to force-drop even if the classifier
     accepted them (curator says "this is enhancement / infra / meta").
   Editing these is the primary curation lever.

Every included issue is bucketed into one of:

- **Novel external source** — the default bucket. New database, new API, new
  dataset that KG-Microbe doesn't cover yet.
- **Salvage from stale PR** — issue title contains `salvaged from … PR #N`
  (convention used since March 2026 for revive-old-work asks).
- **Exploratory** — title verb is `explore` (research-first, transform later).

## When to invoke

- **Whenever the new-transform backlog is discussed.** Regenerate first, then
  reason from the fresh doc.
- **When a novel-source PR merges.** The doc will drop that issue on next
  regeneration (issue is closed, no longer open).
- **After closing duplicates / superseded issues.** Same reason.
- **During quarterly grooming.** Tune `MANUAL_INCLUDE` / `MANUAL_EXCLUDE`,
  regenerate.

## The output doc

`docs/NOVEL_TRANSFORMS.md` is the *only* tracked artifact this skill produces.
The generated file:

- Is fully regenerated on every run (no in-place edits).
- Includes a `<!-- generated by .claude/skills/novel-transforms -->` marker in
  the header so nobody edits it by hand and loses their changes on next run.
- Lists candidates as a sorted table (by issue number ascending) with:
  ``#N | source name | one-line summary | link``.
- Cross-links known duplicates / superseded issues that were closed with a
  cross-reference (from the issue body's "duplicate of #X" convention), so the
  doc stays a useful tombstone for "why isn't ThermoBase X in here?"

## What NOT to put in the doc

- Enhancements to existing transforms (extend bacdive to ingest new columns,
  refactor metatraits pipeline, etc.) — those belong in issue-tracker labels,
  not this doc.
- Cleanup / infrastructure / security issues — same.
- Personal ideas / conversations — file an issue first; the skill will pick it
  up on the next run.
