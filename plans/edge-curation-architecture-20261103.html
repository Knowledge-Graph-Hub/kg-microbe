Plan for release-wide KG-Microbe edge curation

This is the historical architecture review. Subsequent implementation is tracked in the implementation plan.

Prepared 2026-11-03 Pacific / 2026-11-04 UTC. This is a local architecture review and implementation plan, not a new scientific review of the graph. No curation batch, repository creation, deployment, or remote session change was performed.

Recommendation: one new federating Mech, provisionally EdgeMech, with scientific curation delegated to the existing specialist Mechs. Its job is to account for every edge in a pinned KG-Microbe build, connect it to evidence and review decisions, route unresolved work, and produce reproducible curation overlays. Keep bulk graph data and the complete row ledger outside Git. Keep reviewable policies, compact scientific review bundles, schemas, code, manifests, and exception decisions in Git. Do not create one YAML file, test case, issue, agent invocation, or HTML file per edge.

The first deliverable should be an evidence and coverage inventory plus one complete source-to-Mech-to-KG curation round trip. It should establish how much existing reviewed material actually applies before commissioning new literature review at scale.

Curation model and scientific boundaries

Separate six objects rather than treating an edge row as the whole scientific record:

Object

Identity and purpose

Release occurrence

Manifest hash, member, row position and complete row hash; accounts for every occurrence, including duplicates.

Source observation

Versioned source record/assertion and complete normalized payload; preserves relation, provider, methods, conditions, values, units, polarity and evidence.

Scoped claim

A scientific proposition that can group compatible observations without discarding their identity or disagreements.

Evidence item

Pinned source, passage/table/figure or database field, retrieval/version/license metadata, and the experiment or analysis it reports.

Review decision

Exact claim/observation scope, evidence hashes, reasoning, actor type, model/tool versions where applicable, review status and supersession history.

Coverage membership

Explicit, hash-bound list of release occurrences covered by a particular decision or validation policy.

KG-Microbe already hashes the entire normalized observation, not merely subject/predicate/object/relation, in kgx_source.py. Reuse that behavior. A separate occurrence identity remains necessary for exact release accounting; a grouped claim must not collapse independent observations. Bind observation and claim IDs to a named, versioned canonicalization contract and pinned schema/prefix interpretation. Identical payload bytes interpreted under different contexts must not silently acquire the same scientific identity. Canonicalizer changes require explicit migration/alias mappings and review invalidation rules; coordinate this with the context-dependent identity work in PR #1585.

Every released edge receives exactly one current accounting disposition from a mutually exclusive lifecycle such as unprocessed, pending review, admitted, withheld or superseded. Retain multiple historical decisions and disagreements; an explicit versioned current-state view supplies the unique counting row. Validation outcome, review depth, review origin and conflict flags are separate attributes. Thus an admitted row can be structurally validated and matched to a Mech decision without being counted twice. Distinguish upstream-import assurance, scoped Mech review and independently rechecked evidence; publish both their disjoint reporting buckets and detailed attributes. Track agent-assisted review separately from human signoff. Missing or inaccessible evidence is distinct from negative experimental evidence. A withheld mapping is not a globally false biological assertion.

“All edges covered” means no rows fall out of the ledger. It must never be used as a synonym for “all edges independently supported by literature.” Publish separate coverage metrics by predicate, source, review depth, and unresolved reason, with both edge-weighted and distinct-claim/experiment counts.

Use the following review paths:

  1. Ontology and taxonomy imports: verify the pinned source statement, relation semantics, identifiers, taxon/strain scope and transformation. Route scientific or modeling disputes to their owning source. Import validation is an explicit level of assurance, not a fresh literature review of every ontology axiom.

  2. Existing reviewed Mech claims: match exact scientific scope and evidence lineage, import the pinned decision, and retain its limits. Matching names, endpoints, or a passing schema check is insufficient.

  3. New or conflicting biological claims: assemble one coherent evidence packet, ask an agent for a structured decision, run deterministic checks, then perform an independent adversarial review before publishing a supported claim. Escalate ambiguous/high-impact decisions for domain review and allow an unresolved result.

  4. Predictions and text mining: preserve their computational origin and uncertainty. Agreement or a PREGO score is not experimental confirmation.

A packet can cover multiple edges only when it retains a frozen selector, explicit membership, and a reason the same decision applies to each member. Changes to evidence, source version, mapping policy, or claim scope invalidate the affected review. Do not simply carry “reviewed” forward across releases.

Store provenance links across Mechs to detect shared publications, experiments, and copied assertions. KG-derived content subsequently curated in a Mech must not return as independent corroboration of its own ancestor. Evidence graphs, ontological relationships, statistical associations, and biological causal graphs remain different products. Causal interpretation requires the native Mech’s mechanistic evidence and scope rules.

Storage, website and CI design

At a hypothetical 1,000 bytes per edge record, 17.6 million records require 17.64 GB before Git history and filesystem overhead. At 5,000 bytes per HTML page, edge pages require 88.19 GB. These are sizing scenarios, not measured serialization sizes. Both make a per-edge Git/Pages design unsuitable.

GitHub Pages limits published sites to 1 GB and deployments to 10 minutes; the 100 GB/month bandwidth limit is soft. Custom Actions builds are exempt from the soft ten-builds/hour limit, not from the site-size limit. GitHub Pages limits

Use this division:

Location

Contents

EdgeMech Git repository

Schema/contracts, routing rules, small fixtures, reviewed policy changes, bounded review bundles/selected adjudications, release manifests and checksums.

Specialist Mech repositories

Native scientific records, evidence-linked decisions and histories; exporters of explicitly supported scoped assertions.

Versioned artifact storage

Original KGX snapshots; partitioned Parquet observation, membership and decision tables; authoritative complete decision/review histories; evidence snapshots where licensing permits; immutable machine-readable exports.

Local analysis

DuckDB over those versioned files; repeatable full reconciliation and analytical queries.

GitHub Pages

Small release dashboard, aggregate counts, bounded search/index shards, and a reusable record viewer that fetches only the selected packet/detail shard.

Optional read-only query service

Bounded cross-partition filtering and graph queries when precomputed indexes are insufficient; introduced after measuring real reader needs.

Partition the bulk tables by release and stable ID ranges/hash buckets, with source/predicate-aware indexes and columnar row groups. Set partition sizes from a benchmark; avoid an uncontrolled source × predicate × taxon directory fanout. Publish atomically by replacing a small manifest only after every referenced object is verified. Keep all historical manifests addressable.

Bound Git growth as well as page growth: replacing per-edge files with millions of per-packet files would recreate the problem. Full review histories are durable versioned artifacts. Git retains selected authored adjudications, policies and manifests. Large proposed decision changes need deterministic semantic diffs, readable summaries and access to every changed decision for review; approving a hash alone does not approve its scientific contents. Establish tracked-byte, authored-file and Git-object growth budgets, then compact derived indexes without discarding the immutable review history.

Release assets are a suitable initial distribution channel for downloads: GitHub allows up to 1,000 assets per release, each under 2 GiB. The 178 MiB compressed September archive fits, but its uncompressed edge TSV does not fit as one asset. Pack or partition as necessary. These limits do not establish that release hosting is suitable for browser range queries; test CORS, byte ranges and caching, or use object storage/CDN for the interactive data layer. GitHub release limits

Reuse the published ProteinTraitsMech browser pattern: scripts/build_docs_index.py uses lean search shards, bounded detail buckets and exact-ID routing rather than generating a file for every record. Its constants are useful starting points, not evidence that the implementation already scales to this graph. Its authoritative per-record YAML storage and in-memory builder must be adapted to bulk-table inputs; copying the browser pattern alone does not solve ingestion. TaxonMech’s shared viewer is another useful example, but its whole compressed search index should not be copied into a 17.6-million-edge browser.

The viewer should expose the original row, grouped claim, evidence, decision, review depth, unresolved reason, and owning Mech link. Arbitrary edge links should resolve through a release-and-ID URL; they do not need a dedicated HTML file. Show failed data loads distinctly from “no matching records.” Retain offline bulk downloads as a complete access path.

CI validates changes; it does not run literature curation. During iteration, check changed review bundles, their dependency closure, the schema, exporter contracts, and small immutable fixtures. Changes to shared schemas, identifiers, mapping rules or validators trigger broader checks. Run the required code suite once on the final candidate, following KG-Microbe’s now-merged single-suite policy. Validate all rows with streaming data checks, not millions of parametrized tests. ProteinTraitsMech’s published validation_scope.py provides a concrete changed-data/dependency-invalidation starting point. DUFMech’s published Pages workflow provides exact-validated-commit deployment and explicit artifact budgets. CultureMech’s current full-corpus PR job is not the incremental validation pattern proposed here.

Run full corpus reconciliation at release boundaries and after changes that can invalidate broad coverage. Cache by complete dependency fingerprints, including validator/schema versions. Never reuse an old “pass” against changed evidence. Long-running agent tasks belong in resumable leased queues with idempotent writes, bounded concurrency, retry and cost limits; use fleet workers or dedicated batch compute. Do not create an Actions matrix job per edge. GitHub-hosted jobs have a six-hour limit and matrices a 256-job limit. Actions limits

Existing assets and dependent work

The most concrete precedent is MediaIngredientMech. KG-Microbe’s mim_reviewed_release.py validates supported/withheld exports, complete-row hashes and exactly one disposition per source position. Generalize this accounting contract. review_claims.py binds scientific decisions to exact owning-record/evidence bytes and explicitly distinguishes such decisions from integrity receipts.

The basic four-file MIM bundle contains publisher claims about original source/review hashes. KG-Microbe’s schema-v2 pinned-archive consumption can also verify those original bytes. Neither step independently redoes the scientific review. Preserve these distinct assurance levels. The scoped integration issue #1123 is closed; do not schedule it again as wholly unfinished. Its accepted scope does not imply general CultureMech ingestion or approval to replace production mappings.

Dependency-ordered implementation

Wave 0 — establish the denominator and reuse opportunity. Owner: KG-Microbe integration lead, with one fleet-contract reviewer. Preserve the September pilot, select the intended production build, and inventory every row by source, predicate, evidence availability and routing outcome. Join against pinned, eligible reviewed Mech exports; report exact matches, incompatible scope, shared evidence, unmapped IDs and unavailable exports separately. Deliver a machine-readable eligibility/coverage matrix and source-lineage report. Do not promise a reuse percentage until this join is measured. This work can proceed alongside the publication repair.

Wave 1 — shared contract and thin registry. Owner: CLAW contract maintainer and EdgeMech lead. Agree the six identities, review envelope, dispositions, evidence lineage and invalidation rules; version the contract and supply offline positive/adversarial fixtures. Implement an EdgeMech registry over bulk tables, an immutable manifest and a complete pending ledger. Use the MIM exhaustive partition model and KG-Microbe observation/manifest invariants. Deliver one coverage count query and one edge-to-owning-review lookup. Shared schema changes must precede consumer rollout.

Wave 2 — exactly one real end-to-end canary. Owner: one specialist maintainer plus the KG-Microbe adapter owner. Start with a tightly scoped MediaIngredientMech mapping because the reviewed export and consumer already exist. Carry one evidence packet through acquisition/cache, native review, supported/withheld export, EdgeMech membership, KG candidate ingestion, serialized archive and viewer. Verify the persisted artifacts and hashes, a scope mismatch/withhold, and invalidation after a relevant input changes. Use the actual launcher, environment, storage and worker path intended for subsequent jobs. Repair and repeat this canary before any fanout.

Wave 3 — stratified pilot and independent adapters. Once the contract and canary pass, run a bounded pilot of roughly 500–1,000 rows grouped into coherent packets across BacDive/MetaTraits traits, taxonomy, habitat, media and a conflicting/negative-evidence cohort. Preserve source proportions for coverage reporting but oversample difficult cases for error discovery. Evaluate against independently adjudicated evidence, with shared experiments/sources kept out of both sides of a claimed independent evaluation. Estimate time and cost per new packet, reuse rate, abstention/conflict rates and corrected-source impact. This is a proposed sample size, not a powered estimate of graph-wide accuracy.

Parallel work after the shared contract can split into TraitMech provenance, HabitatMech context, TaxonMech mapping, and the browser/storage implementation. Give each native schema/exporter one owner; serialize overlapping CLAW contract changes. Coordinate with existing PRs rather than creating competing writers.

Wave 4 — bounded production queue. Prioritize source/predicate cohorts by downstream use, known defect impact, available evidence and reuse opportunity. Start with systematic provenance/mapping corrections affecting many rows, then unresolved high-value claims. Record leases/checkpoints and deduplicate evidence retrieval; cache only when licenses and source versions allow it. Set budget and concurrency from the pilot. Do not estimate LLM cost as one call per graph row. Forecast total cost as ingestion + unique new packet review + re-review after invalidation + storage/publication, using measured pilot rates and uncertainty.

Wave 5 — reviewed release and continuing updates. Produce an immutable curation overlay and separately named candidate graph. KG-Microbe’s merge is transport of finalized inputs, so semantic corrections must enter the owning transform/mapping and regenerate affected products; do not patch the canonical merge to rewrite meaning. Verify the producer→finalizer→archive round trip and all row dispositions. Publish only after review and the user’s merge/release decision. On the next release, compare observations and evidence dependencies, carry forward only still-valid decisions, and queue additions/changes/removals.

Acceptance and unresolved choices

Acceptance for the first implementation:

  • Every input occurrence appears exactly once in the current accounting ledger; all totals reconcile to the pinned manifest. Every supported outcome resolves to a scoped decision and its evidence or an explicitly named import policy.

  • Independent source observations and contradictions survive aggregation and export. Wrong strain, wrong hydration, changed evidence, copied evidence, missing source and incompatible function scope all produce explicit failures or withheld decisions in adversarial fixtures.

  • One end-to-end canary leaves nonempty, hash-verified artifacts using the production execution path. It proves that path, not rate-limit behavior or accuracy across other source types.

  • Changed-data checks do not scan unrelated scientific records during ordinary iteration. The final code suite and full release data reconciliation still run where required; duplicate full-suite execution is not reintroduced.

  • Proposed initial performance targets: changed-bundle CI below 10 minutes, Pages payload below 250 MB, typical detail data fetch below 2 MB, and a bounded first search response. Initial EdgeMech repository budgets: 250 MB of tracked files, 10,000 authored files and a 1 GB Git-object growth alert. Adjust only from measured workload needs while keeping bulk history outside Git. Benchmark on documented hardware/network; these are targets, not measured performance or platform guarantees.

  • Users can retrieve any edge by ID/release, see what was actually reviewed, follow its owning Mech/evidence, and download the full bulk data.

Before production rollout, settle the repository name, intended production release, durable storage/egress budget, source redistribution permissions, human-review escalation rules and worker budget. None blocks the local inventory or the proposed contract/canary work. No domain-wide evidence review, exact Mech overlap rate, compression benchmark, throughput benchmark or paid-provider cost measurement was performed in this planning review.
